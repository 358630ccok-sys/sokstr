# Incident Runbook: недоступность сервиса (home-lab / production-подход)

Обезличенный пример разбора инцидента из практики эксплуатации home-lab платформы (Proxmox, LXC/VM, Docker, мониторинг).  
Формат: **симптом → диагностика → root cause → устранение → профилактика**.

---

## Контекст
- **Платформа:** Proxmox VE, сервисы в LXC/VM и Docker-контейнерах
- **Наблюдаемость:** Prometheus + Grafana, healthchecks, логи
- **Тип инцидента:** частичная недоступность сервиса (web/API или зависимый компонент), деградация цепочки

## 1) Симптомы
- Сервис не отвечает по HTTP/API или отвечает с ошибками
- В мониторинге/healthcheck — падение доступности или рост ошибок
- Пользовательский эффект: автоматизация/бот/интерфейс не выполняет сценарий до конца

## 2) Первичная диагностика (быстрая локализация)

### Проверка состояния сервиса/контейнера
```bash
# systemd (на хосте/в VM/LXC)
systemctl status <service> --no-pager
journalctl -u <service> -n 200 --no-pager

# Docker
docker ps -a
docker logs --tail 200 <container>
docker inspect <container> --format '{{.State.Status}} {{.State.ExitCode}}'
```

### Проверка ресурсов и базовой доступности
```bash
# Ресурсы
uptime
free -h
df -h
top -b -n 1 | head -20

# Сеть/порт/зависимости
ss -ltnp | grep <port>
curl -I http://127.0.0.1:<port>/health || true
ping -c 2 <dependency_host> || true
```

### Проверка через мониторинг
- Grafana/Prometheus: наличие метрик, CPU/RAM/disk, рестарты, ошибки запросов
- Корреляция по времени: что изменилось перед инцидентом (деплой, обновление, рост нагрузки)

## 3) Углублённая диагностика (поиск первопричины)

Типовые направления и команды:

```bash
# Ошибки приложения/зависимостей в логах
journalctl -u <service> --since "30 min ago" --no-pager
docker logs --since 30m <container>

# Конфигурация и переменные окружения (без вывода секретов в отчёты)
grep -n "^[^#]" /path/to/config | sed 's/=.*/=<redacted>/'

# Проблемы диска/инодов
df -h
df -i

# Проверка DNS/маршрутизации до зависимостей
getent hosts <dependency>
traceroute -n <dependency> || tracepath <dependency> || true
```

## 4) Пример root cause (типовой сценарий)
**Причина:** сервис стал недоступен из-за комбинации факторов (например, исчерпание дискового пространства/ресурса или некорректная конфигурация после изменения), что привело к ошибкам при старте/работе и падению healthcheck.

**Как подтверждено:**
- в логах зафиксированы ошибки записи/подключения/инициализации;
- метрики/системные команды показали деградацию ресурса (disk/RAM/CPU) или отказ зависимости;
- после корректировки конфигурации/освобождения ресурса сервис восстановил работу.

## 5) Устранение (ремедиация)

1. **Стабилизировать сервис:**
   - освободить ресурс / исправить конфигурацию / восстановить зависимость;
   - перезапустить сервис контролируемо:
```bash
systemctl restart <service>
# или
docker restart <container>
```
2. **Проверить восстановление:**
```bash
systemctl is-active <service>
curl -fsS http://127.0.0.1:<port>/health
docker ps --filter name=<container>
```
3. **Убедиться в отсутствии повторных ошибок:**
   - повторно проверить логи и метрики в течение окна наблюдения.

## 6) Профилактика (чтобы не повторялось)

- **Мониторинг/алерты:** пороги по disk/RAM/CPU, алерты на недоступность и рестарты
- **Healthchecks:** автоматические проверки доступности и зависимостей
- **Ресурсные лимиты:** контролировать лимиты контейнеров/VM/LXC, планировать ёмкость
- **Изменения:** фиксировать изменения конфигураций, проверять после деплоя/обновления
- **Документация:** обновить runbook, записать таймлайн, симптомы, root cause и принятые меры
- **Бэкапы/восстановление:** убедиться, что критичные данные и конфиги резервируются и восстановление проверяется
